## EIP-7702 与 ERC-4337 的区别和联系

### 核心区别

|维度|ERC-4337|EIP-7702|
|----|--------|--------|
|层级|应用层标准,不改协议|协议层标准,需要硬分叉|
|上线时间|2023年3月定稿|2025年5月随 Pectra 硬分叉激活|
|实现方式|独立的 UserOperation 交易格式 + Bundler + EntryPoint 合约|新增 Type 4 交易类型,让 EOA 临时"借用"合约代码|
|账户形态|用户需要部署一个全新的智能合约账户地址(通常用 CREATE2)|保留原有 EOA 地址,不需要迁移|
|是否需要硬分叉|不需要,靠 EntryPoint 单例合约实现|需要,因为改变了 EVM 对账户状态的解释方式|

ERC-4337 是应用层账户抽象标准,2023年3月定稿,因为设计上不涉及共识层改动,所以无需硬分叉就能部署,已经在以太坊主网、各个 EVM 二层网络和大多数兼容链上运行了两年多。而EIP-7702 是核心标准track的EIP,随 Pectra 硬分叉于2025年5月7日激活,它引入了 Type 4 交易,携带一组授权列表;每个授权是 EOA 对某个合约地址的签名,交易执行时该 EOA 会临时继承该合约的字节码。

### 各自的运作机制

ERC-4337:用户签署 UserOperation,Bundler 打包这些操作,一个单例的 EntryPoint 合约负责校验并针对用户的智能合约账户执行每一笔操作。整个系统是无需许可的——任何人都可以运行 Bundler,任何人都可以部署智能账户。 

EIP-7702:EVM 之外,该 EOA 依然表现得像普通账户,用户可以通过对零地址签署新的授权来撤销委托,也就是说这种"变身"是逐笔交易、可逆的临时委托,而不是永久性账户转换。

两者的联系(为什么说是互补而非竞争)

1. 技术传承关系:EIP-7702 被认为是通往完整账户抽象(ERC-4337)的关键一步,而且它借鉴了更早的 EIP-3074(引入 AUTH/AUTHCALL 操作码的方案)的思路,但相比 EIP-3074 存在的持久化 invoker 带来的安全风险和向前兼容性问题,EIP-7702 支持逐笔交易级别的智能合约功能,与 ERC-4337 保持一致。

2. 代码高度兼容:EIP-7702 与 ERC-4337 的智能合约钱包代码高度兼容,可以直接复用已经为 ERC-4337 编写和部署的智能合约代码,使现有账户抽象生态的成果不被浪费。

3. 可以组合使用:ERC-4337 和 EIP-7702 并不是竞争关系,两者可以配合使用——让 EOA 变成智能账户的同时,依然可以接入标准的中继器(relayer)和 Paymaster(代付 Gas 的机构)。实践上常见的组合是:用 EIP-7702 让已存在的 2 亿多个 EOA 直接"改装"成智能钱包行为,而 ERC-4337 则更适合从零打造的、原生的智能钱包。用 7702 升级已有地址,再通过 4337 的基础设施路由代付 Gas 或批量操作。

4. 共同的功能集:两者都支持核心的账户抽象功能集:批量交易(一次签名完成多个操作如授权、swap、存款)、通过 Paymaster 实现 Gas 代付(第三方付 Gas,用户账户里可以没有 ETH)、会话密钥(限定范围和时长的临时密钥),以及自定义签名方案、社交恢复、支出限额等。区别在于ERC-4337 原生支持任意签名方案,而 EIP-7702 则要通过所委托的合约来实现。

一句话总结

- ERC-4337 相当于给以太坊搭了一套"平行系统"(新交易格式 + Bundler + EntryPoint),让用户部署全新的智能合约账户,不用动协议本身。

- EIP-7702 则是直接在协议层开了个口子,让你已经在用的旧钱包地址临时"套上"智能合约的能力,解决的是"两亿多个已有 EOA 怎么低成本升级"的问题。EIP-7702 解决了 ERC-4337 单独无法解决的迁移问题——用户的资产、ENS 名称、交易历史、空投资格都留在原有 EOA 上,7702 让他们原地升级而不必迁移到新的智能账户地址;而 ERC-4337 解决的是生态问题——已经存在的 Bundler、Paymaster 和钱包基础设施。


两者结合起来,才是目前业界公认的账户抽象落地路径:用 7702 保留地址身份,用 4337 复用成熟的基础设施生态。

## EIP-7702详解

### 交易结构

EIP-7702 引入了一个新的 EIP-2718 交易类型 Type 4(0x04),也叫 "set code transaction"。它比普通交易多了一个字段:authorization_list。

每个授权元组的格式是`[chain_id, address, nonce, y_parity, r, s]`——本质上就是 EOA 对"我要委托给哪个合约地址"这件事的一份签名。

### 委托的写入过程

对列表中每一个有效的元组,系统会把一个"委托指示符"(delegation indicator)0xef0100 || address 写入这个签名账户(authority)的代码字段。具体规则:

- 这是一个 23 字节的值:3 字节前缀 0xef0100 + 20 字节的目标合约地址。写入后,eth_getCode 查询这个 EOA 会返回这个designator,而不是空的 0x。
- 如果 address 是零地址,则不写入designator(相当于撤销委托),同时清空账户代码,把代码哈希重置为空代码哈希;并把 authority 的 nonce 加一。
- 如果同一笔交易里,同一个 authority 出现了多个元组,以最后一个有效的为准。
- chain_id 可以设为 0,这样这一份签名可以在所有支持 EIP-7702 的链上通用——用户只需签一次名,就能让主网、Arbitrum、Base、Optimism 等多条链上的同一个地址都指向同一个委托合约。

### 执行语义

当有交易发往一个带有委托指示符的 EOA 时,EVM 会加载并执行该指示符指向的合约代码,就像自己的代码一样——这跟 Solidity 里 delegatecall 的效果类似:代码来自委托合约,但存储(storage)和余额(balance)上下文仍然是这个 EOA 自己的。这意味着资产、Nonce、历史记录都不需要迁移到新地址。

一个关键细节:签署 authorization 的账户不一定要等于发起 set-code 交易的 tx.origin——也就是说 Alice 可以签好自己的授权,再让 Bob 或者某个中继商替她把交易广播上链并付 Gas,这是"Gas 代付"能力的来源。

### 典型能力

委托的合约代码运行在 EOA 自己的存储和余额环境里,由此解锁了批量调用、Gas 代付、会话密钥等能力,而不需要把资金迁移到新地址。

### 需要注意的风险

签署一份 EIP-7702 授权等同于把账户的代码执行权交出去——只应该对已知、可信的合约签授权,恶意合约可以包含转走代币、转走 ETH 之类的危险调用,而且这些调用会以你 EOA 的完整权限执行。此外还有一个跨链重放的风险点:当 chain_id 设为 0(全链通用)时,一份钓鱼签名可以在受害者复用同一个 EOA 地址的每一条链上生效,每条链都会把这份授权当作全新且本地有效的来处理,不需要跨链协调或状态共享。

## ERC-4337详解

### 五大组成部分

ERC-4337 标准由四个主要部分构成:UserOperation、Bundler、EntryPoint、合约账户(Contract Account),可选组件还包括 Paymaster 和 Aggregator。

### UserOperation 结构(v0.6)

这是一个代表用户意图的新对象类型,可以理解为结构化的"元交易":包含 sender(智能账户地址)、nonce、initCode(账户尚未部署时的部署字节码)、callData(实际要执行的调用数据)、callGasLimit、verificationGasLimit、preVerificationGas、maxFeePerGas、maxPriorityFeePerGas、paymasterAndData、signature 这些字段。这个结构通过一个独立的 UserOp 内存池传播,而不是走以太坊原本的交易池。

### EntryPoint:两阶段处理

EntryPoint 通过 handleOps 函数接收一批 UserOperation,对每个发送方账户执行校验,然后再触发执行。EntryPoint 强制执行严格的两阶段模式:先校验(verification),后执行(execution)。校验阶段,它会调用每个账户的 validateUserOp 函数,如果附带了 paymaster,还会调用 paymaster 的 validatePaymasterUserOp。只有校验环节不 revert、且遵守存储访问规则,才会进入执行阶段;执行阶段会带上 callData 调用智能账户,这才是真正的用户操作(转账、swap、合约调用、批量操作等)真正发生的地方。

目前生产环境的主流版本是 v0.7,单例合约地址是 0x0000000071727De22E5E9d8BAf0edAc6f37da032,部署在以太坊、Base、Arbitrum、Optimism、Polygon 等主要 EVM 链上;更早的 v0.6 部署在另一个地址,于 2023 年 3 月上线。

### Bundler(打包者)

Bundler 是一种监听 UserOperation 的节点,决定哪些操作有利可图值得打包,然后把它们作为普通以太坊交易的一部分提交给 EntryPoint。Bundler 在把一个 UserOp 接纳进自己的本地内存池之前,会先在链下做一遍校验模拟。

### Paymaster(Gas 代付方)

当 UserOperation 里的 paymasterAndData 字段非空时,EntryPoint 会走一条不同的流程:在校验循环中,除了调用 validateUserOp,handleOps 的执行还必须检查 paymaster 在 EntryPoint 里质押的 ETH 是否足够,然后调用 paymaster 的 validatePaymasterUserOp 来确认它确实愿意为这个 UserOperation 付费。此时 validateUserOp 被调用时,missingAccountFunds 参数会传 0,因为这次的 Gas 不是从账户自己的存款里扣。

值得注意的是 paymaster 至少要质押 verificationGasLimit 三倍的金额,因为这个数值同时也被用作 postOp 调用的 Gas 上限——而 postOp 最多会被调用两次:一次在 UserOperation 执行之后,可能还有一次是失败回滚场景下的补充调用。

### Aggregator(可选)

用于把多个 UserOperation 的签名聚合成一个(比如 BLS 聚合签名),从而在链上摊薄验证成本,适合大规模批量场景,ERC-4337 标准里作为可选组件存在。
